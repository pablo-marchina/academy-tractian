# Load + concurrency benchmark decision — 2026-09-03

## Decision

Add a provider-free, preregistered load/concurrency benchmark over the promoted authenticated PostgreSQL product topology.

The benchmark is deliberately **descriptive**, not a production-capacity certification. It freezes the workload shape before outcomes are observed, measures how the current system behaves under controlled concurrency, and emits aggregate evidence only.

## Why this P0 exists

The product already exposes quantitative runtime telemetry, executor pressure and PostgreSQL-backed ownership, but isolated unit tests do not answer how those components behave together when submissions overlap.

The benchmark closes that evidence gap by measuring:

- submit latency p50/p95/p99/max;
- end-to-end run latency p50/p95/p99/max;
- completed throughput per second;
- accepted/completed/failed/interrupted/uncertain/rejected/timeout counts;
- error rate;
- peak active, queued and inflight runs;
- peak executor utilization;
- process CPU-time delta;
- RSS start/end/peak when available;
- maximum observed persistence p95 during each load level.

No threshold is selected from the observed results.

## Frozen protocol

`research/load-concurrency-protocol-dev-v1.json` is the first frozen DEV protocol:

- concurrency: `1, 2, 4, 8`;
- 24 measured requests per level;
- 2 warmup requests excluded from the measured dataset;
- 30 s completion timeout;
- 25 ms pressure polling.

The protocol hash is embedded in every aggregate report. Any later workload shape is a new protocol/version, not a silent edit to the measured result.

## Measurement boundaries

### CI integration

The PostgreSQL CI integration uses:

- the authenticated signed-bearer product entrypoint;
- a real PostgreSQL service;
- a non-owner/non-BYPASSRLS scoped role;
- two synthetic tenants;
- provider-free deterministic runtime work;
- a bounded executor smaller than the high-concurrency load level so queuing/saturation is observable.

This proves the benchmark contract, concurrent persistence, executor pressure, completion accounting and tenant isolation in one flow.

It does **not** measure Internet/network latency, deployment autoscaling, managed PostgreSQL limits, external TRACTIAN API limits, or model-provider throughput.

### External runner

`scripts/load_concurrency_benchmark.py` runs the same aggregate contract against an already-serving HTTP instance. The bearer token is read only from `ACADEMY_LOAD_BENCHMARK_BEARER_TOKEN`; it is never written to the report.

For a valid provider-free benchmark, the target instance must use deterministic/provider-free decision logic. Pointing the runner at a provider-backed deployment changes the experiment and must be documented as a separate protocol/run.

## Privacy and evidence custody

The report intentionally contains no:

- run IDs;
- organization IDs;
- user IDs;
- identity IDs;
- bearer tokens;
- prompts/user requests;
- raw traces;
- provider material;
- chain-of-thought.

Request identifiers are used only transiently to poll completion and are discarded before aggregation.

## Fail-closed analysis rules

Analysis refuses to produce a report when:

- a preregistered concurrency level is missing;
- an unexpected level appears;
- any request index is missing or duplicated;
- a level has no pressure sample;
- wall-clock duration is missing/non-positive;
- executor-pressure invariants are inconsistent.

Accepted terminal requests require HTTP 202 plus an observed end-to-end duration. Submission rejection and timeout have distinct shapes and cannot be silently converted into successful samples.

## Interpretation

Every report is explicitly:

- `status = MEASURED`;
- `thresholds_preregistered = false`;
- `interpretation = descriptive_only`;
- `production_capacity_claim_ready = false`.

A later capacity/SLO claim requires a separately preregistered acceptance threshold, deployment-representative infrastructure and repeated runs. Those thresholds must be frozen before the candidate outcomes are inspected.

## Promotion boundary

This slice promotes the **measurement capability**, not a new runtime concurrency configuration.

`max_workers`, PostgreSQL pool sizing, queue policy, backpressure, autoscaling or rate limiting must not be changed because one load run "looks better". Any such change is a challenger experiment under EDD with the same frozen workload, hard safety gates and regression checks.

No business-value claim is generated by this benchmark.
